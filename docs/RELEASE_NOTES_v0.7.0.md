# BailingHub v0.7.0：在一个会话里使用多个业务系统

> 发布日期：2026-09-10。升级基线：Core 0.6.1、SDK/DSH 0.4.0。
> 完整客户端配套为 Core 0.7.0、SDK 0.5.0、DSH 0.5.0，三个项目分别发布和安装。
> [English](RELEASE_NOTES_v0.7.0.en.md)

假设你已经接入商城和库存系统，希望对助手说：

> “先查一下保温杯还有多少库存。有货的话，把商城这款商品的售价改为 59 元并上架；没货就先不要上架。”

以前，0.6 配套客户端已经可以在同一会话使用同一系统的多个账户，但不能把不同业务系统的授权一起选入这个会话。本次沿着这条路线继续扩展：在同一中枢内，用户可以先选定多个系统的授权，助手按需要查找各自的工具，再使用对应权限执行，并关联到同一段可见沟通。

以上是通用场景示例，假定两边商品的对应关系已经确认。库存系统需要提供库存查询，商城需要提供改价、上架等业务能力；这些动作不是中枢内置的商城功能，每项操作仍受实际授权和审批约束。

| 这句话中的事情 | 谁来处理 | 完成后查看什么 |
| --- | --- | --- |
| 查询保温杯库存 | 库存系统，使用本次选择的库存授权 | 返回的库存数量和具体商品 |
| 有货时调整商品售价 | 商城系统，使用本次选择的商城授权 | 商城中对应商品的实际售价 |
| 将商品上架 | 商城系统，继续遵守上架权限与审批 | 实际上架结果，或待审批、失败的记录 |

例如，改价已经完成、上架仍待审批时，不能说“全部完成”。管理员可以从同一段沟通追到这两个动作各自的原始执行记录。库存查询反映当时的结果，不等于已经锁定库存，也不建立两个系统的自动库存同步。

## 更新了什么，解决了什么问题

### 新增：一次选择多个系统，按每一步的任务使用对应授权

在示例中，用户先选择商城和库存系统的授权。查询库存使用库存系统的工具与权限；修改售价、上架商品使用商城系统的工具与权限。两个系统即使存在同名的“查询商品”工具，也保留各自的调用归属。

如果这轮只问“商城里这款商品现在卖多少钱”，库存系统不会因为被选中就自动接收完整用户输入、加载业务上下文或被标成已执行。未选中的系统不能被临时加入。第一次发送消息后范围固定，增减授权需要新建会话；已有会话不会自动扩大到新接入的系统。

### 新增：在第一次搜索工具前，先知道系统负责什么

例如，“商城系统”通常负责商品展示、线上售卖和营销活动，“库存系统”负责库存与出入库。管理员可以维护系统名称、简短用途、典型业务方向和边界，配套客户端在首次能力搜索前将已选目标的说明提供给助手。

这样，开发者不必在每一个客户端里硬编码产品词典。系统说明只解释产品定位，实际能调用什么仍要按这份授权查询。“尚未加载”表示工具还未查询，并不表示系统没有能力；读取系统说明本身不创建业务运行记录。

### 新增：授权成功后，显示真实业务对象的名称

例如，用户在商城页面确认授权给“品牌旗舰店”，返回支持此功能的客户端后，可以看到“商城系统 · 品牌旗舰店”。业务后端从已确认的真实对象读取名称，提交给中枢，由 SDK 和插件传给客户端。

这里采用通用的授权主体展示信息，适用于组织、账户、项目、工作区或门店。系统说明负责解释“这是什么系统”，授权名称负责说明“这份授权对应谁”。同名对象不会因此合并，改名也不会重建授权或改变历史会话关联。旧授权缺少名称时明确提示待同步，可由业务后端给原授权补名。

### 改进：从一个入口完成本地智能体的接入配置

管理员打开“智能体客户端 → 接入配置”，依次配置授权入口、系统说明、工具与审批，再检查连接条件。工具目录同时展示动作说明、查询或写入类型与配置状态，减少在接入方和路由页面之间来回寻找。

这些设置仍保存到原接入方和业务路由，不需要重复登记业务系统。原路由的高级权限设置仍保留；集中入口不会自动开放全部写操作，也不能取消业务系统原有的审批要求。

### 新增：业务后端可以找回并管理自己签出的授权

例如，某位商城操作员被停用后，业务后端需要找出对应的智能体会话，收回其查询商品、改价或上架的访问授权。本版补齐已完成换码的授权与最终会话之间的关联，支持接入方查询自己的会话，并按原授权撤销。

业务系统需要把这些接口接到自己的账号停用、租户禁用或权限撤销流程；中枢不会自动订阅这些业务事件。接口只允许查询本接入方的记录，不返回访问凭据。

### 扩展：从完整沟通追到不同系统的原始操作

0.6 已有完整可见对话归档，本版把成员和执行关联扩展到不同系统。管理员可以先看用户的请求与助手回复，再查看库存查询、修改售价和商品上架分别属于哪份授权、哪个系统的执行记录。

某一步等待审批或失败时，不能把其他系统一起描述为完成。恢复归档只补传已经保存的记录，不重复业务写入；历史原文存在保存缺口时继续如实显示。

## 谁需要升级，分别做什么

| 使用方式 | 需要配合的部分 |
| --- | --- |
| 维护 BailingHub 中枢 | 升级 Core，应用本版新增迁移；按需要补充系统说明与接入配置。 |
| 使用 DSH 插件 | 使用本版配套插件及其精确 SDK 依赖；分别授权，在新会话首消息前明确选择目标。 |
| 开发自己的智能体客户端 | 升级 Agent Client SDK / DSH 宿主依赖，核对多系统目标展示、范围恢复、持久存储及名称展示。仅替换包不代表所有界面已自动完成接入。 |
| 维护业务系统后端 | 已接入的业务动作继续沿用。需要自动名称时，升级对应业务 SDK 或按新接口提交主体名称；需要主动回收访问时，对接授权查询与撤销。 |
| 只使用已有同系统多授权 | 原流程保留，旧会话不扩大为多系统；可以按需要采用新增名称与系统说明。 |
| 使用网页聊天、Client API 或其他生态适配器 | 不因本版新增本地会话功能而要求改造成 DSH 客户端；按自身使用方式核对 Core 升级影响。 |

## 如何升级

使用 **Core 0.7.0 + SDK 0.5.0 + DSH 0.5.0**。先准备中枢，再升级客户端；插件会安装精确 SDK 依赖。旧 0.4.0 客户端不会获得新跨系统与名称体验，各发布单元的可用状态以其 Release 为准。

按运维指南备份并准备迁移后，npm 部署可使用：

```bash
npm install --save-exact bailinghub@0.7.0
```

已有 DeepSeek Harness 环境安装配套插件：

```bash
dsh plugin --profile web add dsh-bailinghub@0.5.0
```

自研客户端使用 `bailinghub-mcp-server@0.5.0`。源码部署使用不可变 `v0.7.0` Tag，镜像部署选择 `bailinghub:0.7.0`。完整步骤见[运维指南](OPERATIONS.md)、[安装指南](QUICKSTART.md)和[客户端兼容说明](https://github.com/bailinghub/bailinghub-dsh-plugin/blob/main/docs/COMPATIBILITY.md)。

1. **保留现有数据和配置。** 备份数据库，保留原部署版本，以及客户端原会话范围、真实事件和待传归档记录。
2. **先升级中枢并迁移。** 从 0.6.1 升级新增 058（跨系统会话成员绑定）与 059（授权主体展示信息）；使用正式迁移器按账本执行全部尚未应用的文件。更早版本还要包含各自缺失的历史迁移，不能只手工执行最后两个文件。059 不会自动猜测或回填旧授权名称。
3. **再升级配套 SDK 和客户端。** DSH 的正式包依赖精确匹配的 SDK。自定义存储需要保留多系统范围记录的完整绑定、原会话身份、事件与修订信息；不能用当前授权列表重建旧会话。自定义中枢宿主还需按兼容说明接入新增仓储能力。
4. **按需要完善业务信息。** 管理员填写系统说明；业务后端在授权时提交真实主体名称，或给原有效授权补名。客户端显示最新名称，内部连接与授权身份继续独立保存。
5. **用允许的测试动作核对结果。** 新建会话选择两个系统，先验证查询，再验证一个允许的低风险动作；核对实际目标、后台结果和同一段沟通中的执行关联。需要审批的动作仍应进入原审批流程。

升级后还应检查：只选一个系统时不会访问另一个；同名或改名不会改变授权身份；重开原会话能恢复原范围；只重试归档不会重复业务动作。

如需回退，保留新数据库字段与客户端记录，按对应版本升级指南操作。旧客户端不能据此使用新的多系统范围；遇到不支持时应明确提示，不能通过删除新记录或扩大授权来继续执行。

## 使用边界

- 多系统范围限同一 Hub、同一管理审计域，每个目标使用独立的原 Agent Session；不支持跨 Hub，也不支持把同一个 Session 当作多个所选路由的授权。
- 助手负责规划步骤。本版没有新增持久任务调度、跨系统事务、自动回滚或跨进程恢复未完成业务任务的引擎。
- 不同系统的同名对象或相同编号不代表同一业务身份。关联需要已确认的业务映射或用户明确指定，不能凭展示名猜测。
- 系统查询结果进入本地助手后会参与同一段沟通；完整可见正文归档供中枢管理审计域使用。这不是自动脱敏或跨系统数据共享策略，接入方应选择适合共享的场景。
- 旧版本不支持新字段时显示未知、缺失或不支持，不冒充已加载能力，不自动退回默认授权。
