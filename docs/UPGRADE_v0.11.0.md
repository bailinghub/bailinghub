# 从 Core v0.10.1 升级到 v0.11.0

[English](UPGRADE_v0.11.0.en.md)

## 更新 Core

1. 记录当前镜像摘要或 npm 包版本，以及它使用的配置和数据卷。在现有维护流程中暂停接收任务、排空已接受的工作，保留原制品和可恢复的持久化备份。
2. 按原部署方式切换到 `v0.11.0` 标签对应的镜像、源码，或宿主依赖 `bailinghub@0.11.0`。从 0.10.1 升级无需新增 SQL 迁移。更早的版本仍需逐版核对已发布的迁移。
3. 启动后确认 `/health/ready` 返回 200，再恢复接单。自定义宿主可使用已有模型目录和回执接口读取新增信息。业务系统原有的授权流程和模型服务的输出预算继续适用。[部署运维](OPERATIONS.md)

## 用现有记录验收

| 操作 | 预期结果 |
| --- | --- |
| 在「任务 → 会话」打开一条有消息的历史会话 | 能识别消息来源及角色，并直接看到最新消息。如记录含关联任务，可进入追溯。 |
| 在「调度流」筛选失败状态和一条已知路由 | 列表只显示匹配任务。键盘聚焦状态标签可查看原始状态值。 |
| 在模型服务配置中选定凭证和调用模型 | 支持的路由会显示已核实的窗口。若来源未知，核实后手动填写，或将新服务暂存为停用。 |
| 用有对应服务权限的帐号读取 `GET /usage/v1/model/models` | 按 `service_id` 核对 `context_window_tokens`、服务修订和原有输出预算。窗口是输入与输出合计；旧服务可返回 `null`。 |

若接入方要实现长会话恢复，先通过测试回执核对其对 `CONTEXT_WINDOW_EXCEEDED` 的处理。由宿主保存压缩检查点并为缩短后的新请求分配新操作号。缺少最终回执时先查询原操作；用合成数据验证这一流程即可。[模型续跑](MODEL_CONTINUATION.md)

## 回退

停止新接单并排空后切回先前保存的应用制品，保留本次运行期间的操作、授权和配置修订。旧版界面及宿主仍可使用原读取路径；依赖新增诊断的处理逻辑需接受字段缺失。启动后重新核对就绪状态和一笔原有记录。[版本说明](RELEASE_NOTES_v0.11.0.md)
