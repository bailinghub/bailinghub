# Core Capabilities and Public Evidence

[中文版](IMPLEMENTATION_STATUS.md)

This index separates **ownership, release availability, public evidence, and limitations** for BailingHub Core. Source implementation, test coverage, a formal release, and real business adoption are distinct facts, not a progression of maturity labels. This page is not a third-party certification, a complete security guarantee, or evidence of production adoption.

## Version and evidence conventions

- Formal release baseline: [v0.9.1](https://github.com/bailinghub/bailinghub/releases/tag/v0.9.1), with the [v0.9.1 source Tag](https://github.com/bailinghub/bailinghub/tree/v0.9.1). The existing mechanisms below and the shutdown fix described later belong to this version. This does not mean that every optional feature is enabled by a default installation.
- Historical baseline: [v0.9.0](https://github.com/bailinghub/bailinghub/releases/tag/v0.9.0), commit [`dae5260ede6565080d21e94ae63d52f3a7d23556`](https://github.com/bailinghub/bailinghub/tree/dae5260ede6565080d21e94ae63d52f3a7d23556). Its asynchronous shutdown gap remains documented below. Verify source, npm, images, and deployments separately; updated documentation does not fix old artifacts.
- Test links identify **public test source and the conditions it checks**, not passing runs newly produced by this page. Unit tests, simulated provider responses, MySQL integration tests, and the complete demo have different scopes. Skipped or unexecuted tests are not passing evidence, and do not make an existing mechanism a planned feature.
- Use the [v0.9.1 release notes](RELEASE_NOTES_v0.9.1.en.md) and [upgrade guide](UPGRADE_v0.9.1.en.md) for release contents and prerequisites. Compatible clients, application migrations, provider credentials, storage, and business authorization still require their own configuration and acceptance.

## Ownership and release availability

Core defaults to one organization's management and audit domain. Clients, routes, and tool providers are not organization isolation boundaries. ACC is an independent capability-declaration specification; the business system retains final identity, permission, and business-rule checks. See [Architecture](ARCHITECTURE.en.md), the [wire contract](CONTRACT.en.md), and the [ACC specification repository](https://github.com/agent-capability/agent-capability-contract).

## What the public validation paths establish

### Unit, simulated-provider, and database tests

The linked tests check mechanisms such as authorization, frozen arguments, idempotency, unknown outcomes, allowances, and lifecycle behavior. Database integration tests require their public fixtures' dedicated test configuration. For example, usage MySQL tests explicitly require `BAILING_USAGE_TEST_MYSQL=1`. A default test run that skips them does not establish database acceptance.

Simulated provider responses establish adapter/protocol behavior for the specified inputs, not live-provider availability, pricing, model quality, or production performance. Tests using real MySQL are still not acceptance of a real business integration.

### Public demo and independent reproduction task

The [Docker demo](DEMO.en.md) and [independent validation task](INDEPENDENT_VALIDATION.en.md) provide a public path from installing v0.9.1 through smoke checks and `npm run demo:e2e`. Orders, tickets, refunds, and failure tools use repository demo data. Real model keys, customer APIs, and production credentials are unnecessary.

The task requires concrete results for service startup, console access, anonymous-preview boundaries, smoke checks, and the complete business loop. The README's images and animation show that same public fixture, not customer adoption. Publishing a task card does not establish that an external developer completed it. Reports should retain the actual version, environment, checks, and failure scope.

### Asynchronous model-tool shutdown limitation in formal v0.9.0

The v0.9.0 [model-tool gateway source](https://github.com/bailinghub/bailinghub/blob/dae5260ede6565080d21e94ae63d52f3a7d23556/src/modules/usage/model-gateway.ts) persists provider dispatch, starts background completion/settlement through `void complete().then(...)`, and promptly returns the original request state. The [Kernel close implementation](https://github.com/bailinghub/bailinghub/blob/dae5260ede6565080d21e94ae63d52f3a7d23556/src/app/kernel.ts) explicitly waits for initialization, managed maintenance, HTTP, InHub, execution queues, and resource closure, but does not explicitly register this usage model-tool continuation as a separate drain participant.

Asynchronous-image/original-ID recovery tests in v0.9.0 therefore do not establish that every provider completion is covered by Kernel shutdown acceptance. The public main commit before the fix, [`728899e`](https://github.com/bailinghub/bailinghub/tree/728899e88d89f0ec333684a56640c12154970327), retains the same boundary. This page does not infer observed data loss or duplicate business effects.

### Core v0.9.1 shutdown fix and evidence scope

Core v0.9.1 adds a [background-work tracker](../src/modules/usage/background-work.ts) owned separately by each `UsageRepository`, and drains it before resource closure in the [Kernel close path](../src/app/kernel.ts). Actual registration covers model-tool completion and its late settlement child, settlement after ordinary model responses, traffic-triggered response cleanup/usage reconciliation, and reference-price refresh through persistence. See the [Kernel Host API](KERNEL_HOST_API.en.md) for stopped admission, the shared deadline, and same-instance retry after a timeout. Original HTTP 202 delivery and recovery identifiers remain unchanged. Waiting for close does not issue a new provider request or alter business approval authority.

The new [tracker unit tests](../src/modules/usage/background-work.test.ts) check registration before execution, dynamic children, stopped maintenance, timeout/retry, owner isolation, and failure-diagnostic boundaries. Owner unit tests are not actual multi-Kernel acceptance. The public [Kernel + MySQL lifecycle tests](../src/app/kernel-usage-lifecycle.mysql.test.ts) use actual Kernels, separate test schemas, and synthetic providers to assert delayed completion/late settlement, SQL-lock waits, resource preservation and same-instance retry after timeouts, original-ID/resource isolation between two Kernels, settlement blocking close after ordinary text-model delivery, and standalone shutdown draining before exit. Separate cases cover cleanup and usage reconciliation independently blocking close; reference-price refresh is checked through persistence and stopped new maintenance. Further assertions cover failed settlement retaining the original result/durable pending, later reconciliation without redispatch, diagnostics excluding raw errors, one original dispatch, and one settlement-ledger record. The database tests explicitly require `BAILING_USAGE_TEST_MYSQL=1`. Source/assertions do not substitute for actual results or establish live-provider, process-crash recovery, or production-deployment acceptance.

This fix is available from **Core v0.9.1**, without rewriting the historical guarantees of the v0.9.0 Tag or establishing that a host has been upgraded or deployed. Failed background work may retain durable pending/unknown evidence. Completed drain does not mean every billing record is settled, or provide complete failure-recovery or security assurance.

## General security governance included in v0.9.1

Compared with v0.9.0, v0.9.1 includes prior main-branch additions/updates to the [security self-assessment](https://github.com/bailinghub/bailinghub/blob/v0.9.1/SECURITY_SELF_ASSESSMENT.md), its [Chinese companion](https://github.com/bailinghub/bailinghub/blob/v0.9.1/SECURITY_SELF_ASSESSMENT.zh-CN.md), [Security Insights metadata](https://github.com/bailinghub/bailinghub/blob/v0.9.1/security-insights.yml), the [dependency audit script](../scripts/dependency-audit.mjs) and [tests](../scripts/dependency-audit.test.mjs), plus CI, dependency-update, and package/image exclusion settings. These are public repository governance evidence, not new business-runtime features or a claim that every control passes. Assessments/security metadata are excluded from npm runtime packages and Docker build contents; the assessments retain their stated evaluation baselines.

A version field or this page does not substitute for artifact checks. Evaluate npm, images, and source Tags against their own commit, artifact, and validation evidence. A Core version also does not establish an independent adapter's or host's release status.

## Independent components and non-Core responsibilities

- The [MCP Server and Agent Client SDK](https://github.com/bailinghub/bailinghub-mcp-server), [DeepSeek Harness community plugin](https://github.com/bailinghub/bailinghub-dsh-plugin), [n8n community node](https://github.com/bailinghub/bailinghub-n8n-node), and [executor/OpenClaw adapter](https://github.com/bailinghub/bailinghub-openclaw-skill) are independent projects or adapters consuming public Core interfaces. They have their own versions, configuration, and validation, are excluded from Core artifacts, and do not imply upstream certification, endorsement, or adoption.
- A local host owns its model loop, client credential storage, UI, and approved file sources. Business systems own real execution, permissions, and business invariants. An independent Host owns its platform identity, tenant directory/isolation, and process/upgrade orchestration. Use the [Agent Client guide](AGENT_CLIENT_QUICKSTART.en.md) and [Kernel Host API](KERNEL_HOST_API.en.md) to assess interface responsibilities; Core tests do not prove these external implementations are complete or deployed.
- Complete user-level long-term memory, media tools without executable adapters, and real providers/business systems not accepted through the public paths listed here are not validated capabilities of this index. This page creates no new product timetable for them.

Keep this page and its Chinese companion aligned. Retain the distinction between formal Tags and main, and update a capability's availability or validation scope only when its corresponding public evidence changes.

## Additional process-recovery regressions in current source

[Process crash and lost acknowledgements](MODEL_PROCESS_RECOVERY.en.md) use real SIGKILL, replacement PIDs and withheld MySQL COMMIT acknowledgements to check original requests, provider call counts, results and USD ledgers. These are subsequent opt-in source tests, not part of the historical v0.9.1 Tag. The link states coverage, not a new execution, real-provider or production-crash acceptance claim.
