# 在一次对话里使用多个账户，并看清完整过程

[English](conversations.en.md) · [返回使用者指南](README.md)

如果你管理同一系统里的 A、B 两家门店，过去可能要先切换账户，再分别提问。配套的新客户端可以让你先选好本次对话允许使用的授权，再由 Agent 为每次操作选择对应账户。门店只是示例；它也可以是同一系统中的两个业务账户。

在同一中枢里，也可选择商城与库存两个系统：先查库存，再使用商城允许的改价或上架动作。系统说明解释各自用途，授权名称展示实际业务对象；两边商品映射需已确认。见[v0.7.0 场景说明](../RELEASE_NOTES_v0.7.0.md)。

## 开始前需要什么

部署者准备 BailingHub **0.7.0**；本地客户端使用 **dsh-bailinghub 0.5.0**，它依赖独立的 **bailinghub-mcp-server 0.5.0** SDK。使用自研客户端时，开发者需要接入会话范围、原始可见历史和归档接口。单独升级中枢，不会让旧客户端自动上传完整对话。

业务系统已经接入并开放了需要的操作，你也已经分别完成 A、B 的业务授权。此次升级不要求重写既有业务能力或审批规则。还没有接入业务系统时，先运行[公开 Docker Demo](../DEMO.md)了解查询、审批和执行；该 Demo 不替代多账户客户端的安装与授权。

## 一次完整使用流程

1. **新建对话并选择账户。** 在支持选择范围的客户端中选择 A、B。只选 A 就只能使用 A；不选账户就是普通聊天。DSH 命令行的选择方法见[插件上手指南](https://github.com/bailinghub/bailinghub-dsh-plugin/blob/main/docs/GETTING_STARTED.zh-CN.md)。
2. **说清操作对象。** 例如“分别查询 A、B 的订单，只修改 A 的联系人”。Agent 在本次已选范围里使用对应授权；可以执行什么，仍取决于业务系统开放的能力与当前权限。
3. **按原流程处理审批。** 已完成、待审批与失败的动作分别判断。完整回复不是业务成功的证明，需要时进入原调用或业务后台核对。
4. **从完整沟通进入具体动作。** 中枢管理员打开“任务→会话→客户端完整对话”，先按轮阅读沟通，再打开 A 或 B 的执行记录、工具调用和审批轨迹。“原授权记录”保留原来的查询入口。

首次发出消息后，本次对话的账户范围固定。想换账户就新建对话；重新打开旧对话时恢复原范围，不能自动换成当前默认账户或扩大为全部授权。

## 断网、撤销或保存失败时会怎样

| 看到的情况 | 应如何理解和处理 |
|---|---|
| 待同步 | 业务可能已经完成，沟通记录还没传完。联网后在原会话重试同步，不要为了补记录重新执行修改。 |
| 授权暂时无法核验 | 业务工具保持关闭；联网后在同一会话重试。必须重新核验全部原账户，才能继续补传。 |
| 某个原账户已撤销或身份改变 | 整个原范围保持阻断，不会悄悄只剩另一个账户。 |
| 本地保存失败或历史存在缺口 | 已保存的前半段不代表完整历史。客户端应显示未保存数量或缺口，不能猜补缺失的文字。 |
| 版本不支持 | 检查中枢、SDK和插件配套版本。旧版本的原业务能力不因此自动消失。 |

“已同步”表示当前已保存的事件已上传；还要留意历史缺口或“尚未核对完整历史”的提示。补传只恢复对话归档，不恢复重启后丢失的业务任务，也不会重新发起业务写操作。

## 谁能看到这些记录

完整文字进入你所部署中枢的管理审计空间，供具备任务读取权限的管理员查看。各账户的业务身份、审批与记忆仍分开，混合回复不会被复制到每个账户的模型记忆中。

当前归档范围是客户端实际可见的文本与原执行关联，不包含隐藏推理、附件或任意本地工具的原始输出。只看到了某份授权的执行摘要、却没有完整原文的旧记录，仍会明确表示原文缺失。
